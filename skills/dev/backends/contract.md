# Execution Backend Adapter Contract

The Tech Lead selects `topology` (`serial` or `parallel`) independently from `execution_backend` (`claude-native`, `traycer`, or `incomplete`). Backend selection is deterministic; topology never changes it.

Run `${CLAUDE_SKILL_DIR}/scripts/detect_execution_backend.py` before dispatch. Treat exit status 2 or backend `incomplete` as a pause condition. The detector returns `traycer` in exactly two ways and otherwise fails closed to `incomplete`: both `TRAYCER_AGENT_ID` and `TRAYCER_EPIC_ID` are present in the environment (`backend_source: detected`), or neither is and `.agent/traycer.env` at the worktree root holds both (`backend_source: supplied`). Sources are never mixed: with exactly one identifier in the environment the result is `incomplete` and the file is not used to fill the gap. `claude-native` is selected by the lead for a known native Claude Code session, never inferred from absent identifiers. To discharge the pause as `claude-native`, the lead must have positive evidence the session is native Claude Code (the lead is running `/dev` directly in Claude Code, not through Traycer) and record `backend_source: lead_resolved` in the ledger; a detector-chosen `traycer` records `backend_source: detected` or `backend_source: supplied`, whichever the detector reported. Never use binary presence, model availability, or a failed Traycer preflight to select or fall back to another backend.

**Non-Claude leads.** A lead whose harness is not Claude Code selects `traycer` or records `incomplete` and stops. `claude-native` is never available to it, and the `lead_resolved` discharge above does not apply to it. `lead.harness` is recorded from the Traycer agent list, never inferred. When the detector returns `incomplete` inside a Traycer session with neither environment identifier present, the lead follows the identity acquisition rule in `${CLAUDE_SKILL_DIR}/backends/traycer.md`, which writes `.agent/traycer.env` and re-runs the detector; a lead that cannot obtain both identifiers stops. A partial environment (exactly one identifier) is a host defect: the lead records `incomplete`, reports it to the user, and stops, and the file never recovers it.

Each adapter must implement these operations and either return verified state for the ledger or fail closed:

| Operation | Required verified result |
|---|---|
| `preflight` | Backend identity, host/auth/capability status, and usable launch surfaces |
| `prepare_worktree` | Absolute source and worker paths, assigned branch, base OID, and clean status |
| `resolve_route` | Harness, model, profile behavior/source, reasoning effort, and permission mode |
| `launch` | Distinct agent identity, role, Issue/lane, exact worktree binding, ownership, and the lead's effective `GH_CONFIG_DIR` (literal `"default"` when unset) so the lane's pre-write `check-gh-account` verifies the same login |
| `message` | Assignment payload — including the report-back contract — and backend response/correlation ID |
| `observe` | Agent state, complete cursor-aware replies/transcript evidence, and a report-back shape verdict |
| `shutdown` | Graceful stop result; archive result when requested |
| `recover` | Reconciled live state from `.agent/dev-state.md` without duplicating agents |

## Common invariants

- **Read-only AST guard.** The read-only AST guard in `scripts/validate_skill.py` is an authorship lint, not a security control; behavioural tests and the supported pre-write verification are the real controls. Per ADR-009, this section is the placement so a future round does not re-litigate the guard.
- **Resolve `${CLAUDE_SKILL_DIR}` to its absolute path and substitute it into every prompt before dispatch, in every phase.** Dispatched agents do not inherit `CLAUDE_SKILL_DIR`, so an unsubstituted reference reaches the delegate as literal text it cannot expand. This applies to every lane that pastes prompt content — prototype, worker, QA, and reviewer alike — and to the assignment envelope itself. Record the resolved value as `skill_dir` in `.agent/dev-state.md` and re-resolve it at the start of each run rather than trusting a stored value; the path changes when the Skill is reinstalled, and it is version-stamped when the Skill is installed as a plugin.
- The lead never modifies implementation or test code.
- Every coding agent receives a pre-created, verified branch/worktree and explicit ownership.
- GitHub Issues and PRs are canonical; backend task lists are runtime coordination only.
- Worker → PR → QA → Review is unchanged for both adapters.
- QA and review are distinct read-only SOP roles. Each turn receives no implementation ownership and must leave zero tracked changes; a correction review requires a fresh report.
- The reviewer and QA must have agent IDs distinct from each other and from every implementation worker; the reviewer reviews the recorded current `headRefOid`.
- A new push resets QA, internal review, and external-review completion to pending for the new head; retain prior reports as historical evidence. Run **Review after fixes** in `${CLAUDE_SKILL_DIR}/phases/phase4.md` for fresh results. Internal delta review does not satisfy external review.
- RTK-first command rules apply everywhere. Traycer CLI calls use `rtk proxy python3 ${CLAUDE_SKILL_DIR}/scripts/traycer_cli.py`. Never invoke `traycer` directly, and never through a bare `rtk proxy traycer`.
- Record every transition in `.agent/dev-state.md`; the lead is its sole writer.

## Provider-neutral assignment envelope

Every backend sends the full role prompt plus: role, Issue or review lane, topology, backend, route and route source, branch, absolute worktree, base OID, target `headRefOid` when applicable, ownership, acceptance criteria, plan-approval requirement, RTK rules, reporting channel, the report-back contract from `${CLAUDE_SKILL_DIR}/agents/report-back.md`, and stop condition.

The assignment must not depend on Claude-specific tool names. Native packaging for a non-Claude lead may reuse this contract later; it is not required for Codex, OpenCode, Cursor, or smaller harnesses to serve as Traycer-managed children.

## Report-back enforcement

The report-back is a defect-detection mechanism, not a courtesy. A lane that finishes silently is indistinguishable from one that crashed, and the silence hides whatever the report would have shown. `message` and `observe` therefore enforce it at the adapter layer, in every backend.

- **`message`** embeds the report-back contract from `${CLAUDE_SKILL_DIR}/agents/report-back.md` in the assignment envelope, so the receiving lane carries it as adapter payload rather than only through its role prompt.
- **`observe`** verifies the reply carries all seven required sections by name: Outputs; Commands + exit codes; Deviations; Quality-gate self-assessment; Acceptance criteria; Evidence; Scope / ownership.
- **Recognition is section-heading presence, matched case-insensitively.** A heading with no content under it is a missing section, not a present one — otherwise seven empty headings satisfy the check. Presence is judged mechanically; content is judged by the lead. The adapter never grades what a section says: a stricter parse over free-form prose produces false `incomplete` verdicts, and a check that cries wolf trains the lead to ignore it.
- **A section is present when its heading is followed by at least one line containing a non-whitespace character, before the next heading of any level.** That is the whole test, and it is deliberately crude: an empty code fence counts as present, because its fence lines are non-whitespace. Refusing to count them would mean parsing structure and judging emptiness, which is the judgment this floor exists to remove — "is anything there" is decidable, "is this substantive" is not. Two leads applying this rule to the same reply reach the same verdict.
- A reply missing any of the seven sections is malformed adapter output. Mark the operation `incomplete`, record it in `.agent/dev-state.md`, and never infer completion. **A lane that never replied at all is the same verdict, not a lesser case.** Absence of a report is not a report.
- **The verdict never varies; the recorded cause does.** Record `report_back: incomplete` with cause `absent` (a `completed` read carried no reply correlated to the recorded response ID), `malformed` (a complete reply arrived without every section), or `truncated` (the read ended without the transport declaring the reply complete, whether or not a correlated reply was seen). The verdict is identical because all three leave the lane unverified. The cause differs because the remedy does: `absent` questions whether the lane is alive at all and is answered by inspecting live state before re-requesting or replacing the lane; `malformed` comes from a demonstrably alive lane and is answered by re-requesting the shape at the recorded response ID; `truncated` is re-read before it is re-requested, because the missing sections may already exist upstream of the cut.
- **A verified report is recorded too, not only a failed one.** A lane whose correlated reply carried all seven sections records `report_back: complete`; a dispatched lane not yet observed stays `pending`. The fields and their allowed values are the report-back record schema in `${CLAUDE_SKILL_DIR}/templates/DEV_STATE_TEMPLATE.md`, and the cause is never omitted on an `incomplete` verdict. Without the positive record, a lane that reported cleanly and a lane nobody ever looked at occupy the same absence in the ledger — this contract's own failure mode, one level down.
- **`absent` is classified first, before any shape or paging classification runs.** The read still happens first — nothing can be known to be absent without looking. What comes first is the *classification*: once the read ends, ask whether a reply correlated to the recorded response ID was observed at all, and if none was, record the read's terminating condition and stop, with cause `absent` when that condition was `completed` and `truncated` when the read was cut. The shape branch below never runs on an empty read. This precedence is part of the taxonomy rather than each adapter's discretion, because the shape branch misclassifies silence when it runs first: a surface that returns an empty message as complete would reach it and record `malformed` — seven sections missing from nothing — sending the lead to re-request a shape from a lane that may be dead, where `absent` says to inspect whether it is alive at all. **An empty read is never evidence of a reply's shape.** What an empty read *is* evidence of is its own transport, which is why its terminating condition is recorded rather than discarded: that condition is the whole difference between a lane that did not reply and a read that stopped too early.
- **Judge shape only after the reply is complete per the transport's own completion signal.** Consume every cursor/page first. Calling a first page malformed manufactures a lane defect out of pagination.
- **Paging must be bounded, and the bound is what makes `truncated` reachable.** "Read until the transport declares completion" is unbounded on its own: a transport that never declares it leaves `observe` looping forever, and the cause that exists for exactly that state is never recorded. Every adapter therefore ends its read on the first of four conditions — the transport declares the reply complete (`completed`); a page returns no new content or a cursor that does not advance (`stalled`); a page cap is reached (`page_cap`); a time bound elapses (`time_bound`). Those four names are the ledger's `report_back_termination` values, and the contract, both adapters, and `${CLAUDE_SKILL_DIR}/templates/DEV_STATE_TEMPLATE.md` use exactly them. Each adapter states its own cap and bound as concrete values, because a page size and a timeout are properties of that transport, not of this contract. An adapter that names no bound has not implemented `observe`. Every bounded read records which of the four ended it, a read that found no correlated reply included — that condition is what separates the two empty cases: no correlated reply after `completed` is `absent`, and no correlated reply after `stalled`, `page_cap`, or `time_bound` is `truncated`.
- **Termination decides whether section inspection is permitted.** For a reply that was observed, this is what keeps `truncated` and `malformed` apart in practice, `absent` having already been ruled out above: the adapter records the terminating condition, so a lead reads it rather than guessing from the text. A read ended by the completion signal is judged on its sections — all seven present is a report; any missing is `malformed`. A read ended by a stall, the page cap, or the time bound is `truncated`, **whatever sections it happens to contain** — including all seven, because content under a heading can be cut mid-section, and a report that may be missing its tail is not a report that passed. Fail closed toward `truncated`: re-reading a complete reply costs a read, while accepting a cut one accepts the silence this contract exists to detect.
- **Record the terminating condition, and derive the verdict and cause from the full mapping.** Use the observed termination, reply correlation, and section presence as the inputs to the mapping table in `${CLAUDE_SKILL_DIR}/templates/DEV_STATE_TEMPLATE.md`; the verdict and cause must match that row. Keeping the condition matters because the cause is lossy by design: `stalled`, `page_cap`, and `time_bound` all collapse to `truncated`, which is everything the remedy needs and nothing a lead needs to see that one transport stalls on every lane while another rarely reaches its bound. A lane with no correlated reply still ran a bounded read — absence is established by reading, not instead of reading — so its termination is recorded like any other. `absent` is not a fourth terminating condition; it is a cause, and the condition that established it is `completed`. **A cut read that found no correlated reply has not established absence at all**: the reply may lie past the cut, so that record is `truncated` and the remedy is to re-read before concluding anything about the lane. Only `null` means no read has been performed, which is the `pending` state.
- **Swap-time evidence is adapter-defined, narrow, and fails closed.** When a transport delivers replies by push, a lead change can leave every inbox empty although the lane reported, and the previous lead's transcript is the only surviving evidence. An adapter may define a rule that lets that transcript satisfy correlation, and any such rule is bound by four constraints. It applies only after a lead change recorded in the ledger, and only when the bounded reads for the new and the previous lead ended `completed` with no correlated reply. It accepts only a message from the recorded lane agent, after the recorded dispatch, that names the recorded response ID in full, and anything less stays `absent`. It never upgrades a read that ended `stalled`, `page_cap`, or `time_bound`: a cut read stays `truncated`, and a cut transcript read cannot establish absence. It adds no row, termination value, or cause to the mapping in `${CLAUDE_SKILL_DIR}/templates/DEV_STATE_TEMPLATE.md`; it only decides whether a reply counts as correlated. The Traycer adapter defines this rule in `${CLAUDE_SKILL_DIR}/backends/traycer.md`, because Traycer acknowledges pushed replies and drains the inbox. A backend without that drain needs no such rule, and none is defined for it.
- Role-specific close-outs in `${CLAUDE_SKILL_DIR}/agents/report-back.md` are additive and never substitute for the seven required sections. A QA lane that posts its PR-comment template and replies nothing has not reported.

## Child-harness capability checklist

A dispatched child harness is **valid** for a Traycer-managed lane iff **all four** of the following hold. The check runs at first dispatch for the lane and is recorded in `.agent/dev-state.md`. An unmet item fails the lane closed to `incomplete`; the remedy is always a different route — a child that satisfies the checklist, or the lead dispatching directly when no child qualifies — and **never a trimmed prompt, never a relaxed checklist**. This rule is pinned: removing the sentence "remedy is a different route, never a trimmed prompt" is itself a gate failure (doc-assertion test).

A valid child harness:

1. **receive-capable GUI surface.** The child accepts the assignment payload (full role prompt + provider-neutral envelope + report-back contract) and can reply on an arrival surface where the lead's `observe` step can correlate replies to recorded response IDs. A pure headless / non-interactive child fails here.
2. **Tooling on PATH.** `rtk`, `gh`, and `python3` are all resolvable to executable binaries on the child's PATH. The Skill assumes the host already has these (RTK install is an ambient prereq; `gh` is per the GitHub CLI docs; `python3` is standard).
3. **Shared-filesystem read of resolved Skill files.** The child can read the resolved `agents/report-back.md` and `phases/repository-context.md` (i.e., the files the lead resolved via `${CLAUDE_SKILL_DIR}` substitution) and can run `${CLAUDE_SKILL_DIR}/scripts/resolve_repository.py`. The lead substitutes absolute paths into every prompt before dispatch; the child does not need to expand `${CLAUDE_SKILL_DIR}` itself.
4. **Replies in seven-section shape on arrival surface.** The child's report-back reply contains every required section by name: Outputs; Commands + exit codes; Deviations; Quality-gate self-assessment; Acceptance criteria; Evidence; Scope / ownership. A missing or empty section is `report_back: incomplete` per the Report-back enforcement section above; this rule is the same rule, applied at the child surface rather than the adapter surface.

Unmet item → `incomplete`. **Remedy is a different route, never a trimmed prompt.** This sentence is pinned (doc-assertion test).
